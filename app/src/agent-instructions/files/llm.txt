# JobCRM — JAA entry point

**Required Env Vars**
JOBCRM_APP_URL: APP Frontend url (for instructions)
JOBCRM_API_ORIGIN: API Server url
JOBCRM_X_API_KEY: x-api-key for agent access

In case any of these two is missing, request human for further action.

If all is available, read below instructions:

Read these from the **web app origin** (same host/port as the UI in dev), not the API port unless you proxy them together.

| Resource | Path | Purpose |
|----------|------|---------|
| Model architecture | GET {JOBCRM_APP_URL}/model-architecture.md | Entities, relationships, workflows, `research_status`, archive behavior |
| API contracts | GET {JOBCRM_APP_URL}/api-contracts.md | JAA routes: query params, JSON request/response shapes |
| MCP hints | GET {JOBCRM_APP_URL}/mcp-guidance.md | Polling and enrichment flow |

**Authoritative JSON schemas**: OpenAPI at `{JOBCRM_API_ORIGIN}/docs` (e.g. http://localhost:8000/docs). Use `api-contracts.md` for a single JAA-oriented narrative; use `/docs` for exact field lists and enums.

**Auth**

- Agent: `X-API-Key: {JOBCRM_X_API_KEY}` on `/api/v1/agent/*`

**Base paths (JOBCRM_API_ORIGIN)**

- API: `/api/v1/...`
- Agent: `/api/v1/agent/...`

**Quick JAA route list** (lookup level; full contracts in `api-contracts.md`)

- GET `/api/v1/agent/health` — liveness + lightweight DB connectivity check (`status`, `api`, `database`).
- GET `/api/v1/agent/applications/company-research-pending` — applications in `company_research_pending`, FIFO oldest first, max 50 (default 5).
- GET `/api/v1/agent/applications/ppa-pending` — applications in `ppa_pending`, FIFO oldest first.
- GET `/api/v1/agent/applications/application-pending` — applications in `application_pending`, FIFO oldest first.
- GET `/api/v1/agent/applications` — list/search applications with filters (`status_filter`, `exclude_status`, `email_sent`, `company_id`, `applied`, pagination/sort).
- GET `/api/v1/agent/applications/{id}` — fetch one application by id (same shape as user `GET /api/v1/applications/{id}`); use when you already have the id and do not need to list.
- GET `/api/v1/agent/applications/{id}/per-profile-applications` — fetch all per-profile rows for one application id (ordered by `order_index`, then `created_at`).
- PUT `/api/v1/agent/applications/{id}` — update application fields/status; use for lifecycle moves (`company_researching`, `ppa_pending`, `application_ready`, `archived`, etc.); include optional `archive_reason` when archiving.
- GET `/api/v1/agent/companies/unindexed` — companies with `research_status=pending` (research backlog), oldest-first FIFO, max 5.
- PUT `/api/v1/agent/companies/{id}` — update one company profile/enrichment fields (`overview`, `full_product_detail`, `full_hiring_detail`, `full_organization_detail`, `analysis_links`, `research_status`, or legacy `indexed` mapped to `research_status`, etc.).
- PATCH `/api/v1/agent/companies/bulk` — batch company updates in one request (`updates[]` of `{company_id, payload}`).
- POST `/api/v1/agent/workers/assign/{worker_kind}` — no body; `{worker_kind}` is `company-researcher` | `ppa-analyser` | `application-drafter`; returns `{ "lease_id" }` if a slot is free (**404** unknown kind, **409** if max concurrent workers reached).
- POST `/api/v1/agent/workers/release/{worker_kind}` — body `{ "lease_id": "<id from assign>" }`; path kind must match the lease (**400** if lease is for a different worker kind).
- GET `/api/v1/agent/workers/count/{worker_kind}` — `{ "active": <n>, "max": <n> }` for that stage (read scope).

**Human (JWT) settings** (same app, not agent key): `GET/PATCH /api/v1/settings/workers` for max worker limits; `POST /api/v1/settings/workers/release-all` with `{ "worker_type": "..." }` to clear all leases of that type.

- GET `/api/v1/agent/profiles/ids` — lightweight profile id scan for planning/matching.
- GET `/api/v1/agent/profiles/{id}` — full profile detail (bio, niche, resume/context) for tailoring.
- GET `/api/v1/agent/profiles` — paginated profile listing when bulk context is needed.
- POST `/api/v1/agent/per-profile-applications` — create a PPA record for a chosen profile under an application.
- PUT `/api/v1/agent/per-profile-applications/{id}` — update PPA analysis outputs (`fit_score`, `analysis`, `tailored_resume_link`, `cold_email_plan`).
- POST `/api/v1/agent/emails` — create tracked outbound drafts/follow-ups tied to a PPA.
- POST `/api/v1/agent/notifications` — create user-facing notification events (`user_id`, `notification`, `type`, optional `timestamp`, optional `check`, `payload` with `id` + `message`). See api-contracts.md.
- GET `/api/v1/agent/industries` — read industry taxonomy; supports pagination/search for large catalogs.
- POST `/api/v1/agent/industries` — create one industry taxonomy entry.
- POST `/api/v1/agent/industries/bulk` — create 1-50 industries in one request.
- PUT `/api/v1/agent/industries/{id}` — update an industry taxonomy entry.

Agent writes are scoped to Company, Application, PerProfileApplication, Email, Notifications (see server policies).
