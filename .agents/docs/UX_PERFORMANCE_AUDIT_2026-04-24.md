# UX And Performance Audit - 2026-04-24

## Scope
- Static audit of frontend UX, API route shape, backend repository behavior, and agent-facing flows.
- Severity scale: Critical, High, Medium, Low.
- No runtime benchmark was run; findings are code-evidence based.

## Issues

| ID | Severity | Area | Short Description | Evidence | Why It Matters | Suggested Direction |
| --- | --- | --- | --- | --- | --- | --- |
| UXPERF-001 | Critical | Backend persistence | Mongo writes delete and reinsert every collection on most mutations. | `MongoRepository._sync()` rewrites all collections, and `_sync_collection()` does `delete_many({})` then `insert_many()` for every model set in `crm/app/repository.py:1408` and `crm/app/repository.py:1420`. Almost every create/update/delete calls `_sync()` in `crm/app/repository.py:1432`. | Every small user action or agent write becomes O(total database size). Concurrent writes can lose data because one request rewrites stale in-memory collections over another request's changes. | Replace full-sync repository with per-collection Mongo CRUD operations using atomic update/insert/delete. Add indexes and transactional/bulk paths where needed. |
| UXPERF-002 | Critical | Agent bulk writes | Bulk company updates can trigger dozens of full database rewrites in one request. | Agent bulk company route loops updates in `crm/app/main.py:1289`; each `repo.update_company()` calls `_sync()` in `crm/app/repository.py:1452`, and each audit event calls another `_sync()` in `crm/app/repository.py:1548`. | A 50-company bulk enrichment can become about 100 full database rewrites, blocking the agent workflow and making production latency explode. | Add real bulk update and bulk audit persistence. Persist each changed collection once per request, or move to native Mongo bulk operations. |
| UXPERF-003 | High | Backend architecture | Production reads load entire Mongo collections into process memory. | `MongoRepository._load()` reads every collection with `.find()` at startup in `crm/app/repository.py:1386`; list methods then operate on dictionaries in memory. | Startup time and memory grow with database size. Multiple API processes can drift stale because reads do not query Mongo after startup. | Query Mongo directly for read paths. Keep memory repository for tests/dev only. |
| UXPERF-004 | High | API list performance | List endpoints scan, filter, and sort full in-memory collections before slicing. | Companies scan/filter/sort at `crm/app/repository.py:505`; profiles at `crm/app/repository.py:744`; applications at `crm/app/repository.py:848`; audit and notifications also scan/sort at `crm/app/repository.py:1124` and `crm/app/repository.py:1163`. | Pagination does not bound server work. Every list page still costs O(all rows), and sort/search cannot use indexes. | Push filters, sort, skip, limit, and projection into Mongo queries. Add indexes for status, company_id, applied, updated_at, created_at, user_id, read_at. |
| UXPERF-005 | High | API safety | Several human list endpoints accept unbounded `limit`. | `limit: int = 50` without `Query(..., le=...)` appears on company/application/profile/notification/audit routes, e.g. `crm/app/main.py:365`, `crm/app/main.py:617`, and `crm/app/main.py:1036`. | A user, bug, or browser call can request huge pages, causing large payloads and full render work. | Add consistent max limits and return pagination metadata. Prefer 25-100 for UI lists and separate export endpoints for large pulls. |
| UXPERF-006 | High | Dashboard API | Dashboard metrics fetch up to 10,000 application rows and 200 notifications, then count in Python. | `dashboard_metrics()` calls `repo.list_applications(limit=10_000)` and `repo.list_notifications(limit=200)` in `crm/app/main.py:198`. | Dashboard first load grows with application count and can undercount unread notifications above 200. | Add repository count/aggregate methods that return counts only. Use Mongo `count_documents` or aggregation. |
| UXPERF-007 | High | Search API | Global search scans long text fields in memory and returns weak application labels. | Search scans company overview, profile bio, and application notes in `crm/app/repository.py:1074`; dashboard displays application result as status plus id slice in `app/src/pages/DashboardPage.tsx:100`. | Search gets slower as rich AI content grows, and application results are hard for users to recognize. | Add indexed/full-text search, searchable application company/job fields, and result summary fields like company name, job title/link, status, updated date. |
| UXPERF-008 | High | Agent queues | Agent queue endpoints scan all matching applications/companies and return full objects. | Agent pending routes call `list_applications_by_status()` in `crm/app/main.py:1178`; that method scans all applications at `crm/app/repository.py:876`. Company research queue scans companies at `crm/app/repository.py:518`. | Polling agents amplify O(all rows) scans. Returning full application/company bodies wastes payload when workers only need id, status, and priority fields first. | Add indexed queue queries with compact task summary responses. Fetch full detail only after a worker claims a task. |
| UXPERF-009 | High | Application detail API | Application detail bundles PPA emails with per-PPA scans over all emails. | Detail route loops PPAs and calls `repo.list_emails_for_ppa()` at `crm/app/main.py:719`; `list_emails_for_ppa()` scans all emails in `crm/app/repository.py:1269`. | Detail load cost becomes O(PPAs * all emails). Rich outreach history will make the primary review screen slow. | Batch load emails for all PPA ids in one indexed query. Consider summary-first render with lazy email body expansion. |
| UXPERF-010 | Medium | Applications page | Applied-profile filter loads all profile summaries on mount and again after every list load. | `listAllProfileSummaries()` pages until exhausted in `app/src/api.ts:145`; `ApplicationsPage` calls it on mount and again after each page load in `app/src/pages/ApplicationsPage.tsx:58` and `app/src/pages/ApplicationsPage.tsx:159`. | Application list fetch count grows with profile count and repeats during normal paging/sorting. | Add a bounded filter-options endpoint, cache longer with invalidation, or derive applied profile facets from server-side filtered results. |
| UXPERF-011 | Medium | Applications UX | Company search and applied-profile filters only filter the current page. | Server fetch is paged in `app/src/pages/ApplicationsPage.tsx:149`; company search filters `items` locally at `app/src/pages/ApplicationsPage.tsx:104`; applied profile filter also filters current `items` at `app/src/pages/ApplicationsPage.tsx:112`. | User may see "No applications in this view" even when matches exist on another page. Filters feel unreliable. | Move company/profile filters to API query params. Reset to page 1 on filter changes and return total/has_next from server. |
| UXPERF-012 | Medium | Applications UX | Applied-profile filter UI presents all profile names, not only profiles present in current result set. | Options come from all profile summaries at `app/src/pages/ApplicationsPage.tsx:58`, then render every name in the popover at `app/src/pages/ApplicationsPage.tsx:462`. | Filter can show many irrelevant choices and hide rows unexpectedly. "All profile filters" is also hard to understand. | Use server-provided facets or only show matching facet counts. Rename action to "Reset profile filter" if kept. |
| UXPERF-013 | Medium | Worker state UX/perf | Non-admin list pages repeatedly call admin-only worker settings and swallow failures. | Applications fetch `api.getWorkerState().catch(() => null)` on each load in `app/src/pages/ApplicationsPage.tsx:152`; Companies does similar in `app/src/pages/CompaniesPage.tsx:95`; backend route requires admin in `crm/app/main.py:1128`. | Non-admin users generate avoidable 403s on every list load. Admin users also pay another request for each page/sort/filter change. | Gate worker-state calls by role or expose a lightweight readable worker summary endpoint if all roles should see it. Cache briefly. |
| UXPERF-014 | Medium | Company detail | Company detail fetches full industry catalog, and the picker renders unbounded `<option>` and suggestion lists. | `CompanyDetailPage` calls `getAllIndustries()` with `api.getCompany()` in `app/src/pages/CompanyDetailPage.tsx:82`; `getAllIndustries()` pages until exhausted in `app/src/state/industryCatalog.ts:26`; `IndustryMultiSelect` renders all unselected industries in a `<select>` at `app/src/components/IndustryMultiSelect.tsx:77`. | A large taxonomy makes company detail slow and creates a large DOM. | Use a server-side searchable multi-select with a small limit and keep selected industries hydrated locally. |
| UXPERF-015 | Medium | Industries UX | Industries page only fetches 200 rows and has no pagination. | `IndustriesPage.load()` sets `limit=200` in `app/src/pages/IndustriesPage.tsx:27`; table renders the fetched `items` only in `app/src/pages/IndustriesPage.tsx:227`. | Users cannot browse beyond the first 200 industries unless search happens to find them. The "Visible industries" stat is not total count. | Add normal pagination, total/visible counts, and server-side search state. |
| UXPERF-016 | Medium | Notifications API/UI | Notification polling uses two requests every 45 seconds and list enrichment does per-row entity lookups. | Layout poll calls unread count then `listNotifications(limit=25)` in `app/src/components/Layout.tsx:90`; list route enriches each notification at `crm/app/main.py:1046`; link computation looks up app/company/email/ppa rows in `crm/app/notification_links.py:18`. | Multiple tabs/users create constant background load. Per-row enrichment gets more expensive as notification volume grows. | Return count and newest unread notifications from one endpoint, store notification links at creation time, or batch-resolve links. |
| UXPERF-017 | Medium | Notifications UX/perf | Bulk mark-read sends one request per selected notification. | `handleBulkMarkRead()` uses `Promise.all(unreadSelected.map(...api.markNotificationRead))` in `app/src/pages/NotificationsPage.tsx:121`. | Even page-sized batches create request bursts and partial-failure ambiguity. | Add `POST /notifications/read` bulk endpoint that accepts ids and returns count. |
| UXPERF-018 | Medium | Companies API payload | Company list endpoint returns full `Company` objects for table views and search pickers. | Route is `response_model=list[Company]` in `crm/app/main.py:365`; frontend table/pickers call `api.listCompanies()` in `app/src/api.ts:126` and `app/src/components/NewApplicationModal.tsx:100`. | Tables and pickers do not need overview, detailed research links, source links, and full enrichment fields. Payload grows as AI research content grows. | Add `CompanyListItem` or summary endpoint with id, name, website, research_status, has_application, updated_at. |
| UXPERF-019 | Medium | Company state freshness | Company list page cache can show stale rows for up to 5 minutes after agent or other-tab changes. | Company summaries cache has 5-minute TTL in `app/src/state/companySummaries.ts:5` and normal page loads reuse it in `app/src/state/companySummaries.ts:32`. | Agent research/status updates may not appear when users navigate back to the list, causing trust issues. | Invalidate on visibility focus or use shorter TTL/stale-while-revalidate. Keep cached shell but refresh in background. |
| UXPERF-020 | Medium | Profile/industry destructive UX | Several destructive actions use native confirm dialogs with little context and no impact preview. | Profile freeze/delete in `app/src/pages/ProfilesPage.tsx:115`; profile detail delete in `app/src/pages/ProfileDetailPage.tsx:161`; industry delete in `app/src/pages/IndustriesPage.tsx:145`; email delete in `app/src/pages/ApplicationDetailPage.tsx:411`. | Native confirms are easy to misclick, inconsistent with app modals, and cannot show related impact or recovery guidance. | Replace with app modals for deletes/freezes. Show affected related rows, require typed confirmation for high-impact deletes, and disable while submitting. |
| UXPERF-021 | Low | Profile UX | Profile save navigates away immediately, with no success state or unsaved-change protection. | `ProfileDetailPage` navigates to `/profiles` after save in `app/src/pages/ProfileDetailPage.tsx:145`. | Long markdown edits can feel risky; accidental navigation or failed mental confirmation hurts confidence. | Show inline saved state and stay on detail, or add unsaved-change guard for dirty long-form forms. |
| UXPERF-022 | Low | Pagination UX | Tables infer `hasNextPage` from page length and show no total count. | Applications sets `hasNextPage` from `items.length === PAGE_SIZE` in `app/src/pages/ApplicationsPage.tsx:156`; same pattern appears in Companies, Profiles, Notifications, Audit. | Exact-final-page sizes can show a dead next page, and users cannot tell result size or jump to page. | Return `{items,total,has_next}` or cursor metadata from API and update `TablePagination` to show result count and robust next state. |

## Priority Order
1. Fix repository persistence and query architecture first: UXPERF-001 through UXPERF-004. These are core scalability blockers.
2. Fix dashboard/search/agent queue hot paths next: UXPERF-006 through UXPERF-009.
3. Move page-local filters and full-catalog frontend fetches to bounded server APIs: UXPERF-010 through UXPERF-015 and UXPERF-018.
4. Polish user trust flows: UXPERF-016 through UXPERF-022.
