# UX And Performance Audit - 2026-04-24

## Scope
- Static audit of frontend UX, API route shape, backend repository behavior, and agent-facing flows.
- Severity scale: Critical, High, Medium, Low.
- No runtime benchmark was run; findings are code-evidence based.

## Issues

| ID | Severity | Area | Short Description | Evidence | Why It Matters | Suggested Direction |
| --- | --- | --- | --- | --- | --- | --- |
| UXPERF-001 | Critical | Backend persistence | Mongo writes delete and reinsert every collection on most mutations. | `MongoRepository._sync()` rewrites all collections, and `_sync_collection()` does `delete_many({})` then `insert_many()` for every model set in `crm/app/repository.py:1408` and `crm/app/repository.py:1420`. Almost every create/update/delete calls `_sync()` in `crm/app/repository.py:1432`. | Every small user action or agent write becomes O(total database size). Concurrent writes can lose data because one request rewrites stale in-memory collections over another request's changes. | Replace full-sync repository with per-collection Mongo CRUD operations using atomic update/insert/delete. Add indexes and transactional/bulk paths where needed. |
| UXPERF-002 | Critical | Agent bulk writes | Bulk company updates can trigger dozens of full database rewrites in one request. | Agent bulk company route loops updates in `crm/app/main.py:1289`; each `repo.update_company()` calls `_sync()` in `crm/app/repository.py:1452`, and each audit event calls another `_sync()` in `crm/app/repository.py:1548`. | A 50-company bulk enrichment can become about 100 full database rewrites, blocking the agent workflow and making production latency explode. | Add real bulk update and bulk audit persistence. Persist each changed collection once per request, or move to native Mongo bulk operations. |
| UXPERF-003 | High | Backend architecture | Production reads load entire Mongo collections into process memory. | `MongoRepository._load()` reads every collection with `.find()` at startup in `crm/app/repository.py:1386`; list methods then operate on dictionaries in memory. | Startup time and memory grow with database size. | UXPERF-004 | High | API list performance | List endpoints scan, filter, and sort full in-memory collections before slicing. | Companies scan/filter/sort at `crm/app/repository.py:505`; profiles at `crm/app/repository.py:744`; applications at `crm/app/repository.py:848`; audit and notifications also scan/sort at `crm/app/repository.py:1124` and `crm/app/repository.py:1163`. | Pagination does not bound server work. | UXPERF-005 | High | API safety | Several human list endpoints accept unbounded `limit`. | `limit: int = 50` without `Query(..., le=...)` appears on company/application/profile/notification/audit routes, e.g. `crm/app/main.py:365`, `crm/app/main.py:617`, and `crm/app/main.py:1036`. | A user, bug, or browser call can request huge pages, causing large payloads and full render work. | Add consistent max limits and return pagination metadata. | UXPERF-007 | High | Search API | Global search scans long text fields in memory and returns weak application labels. | Search scans company overview, profile bio, and application notes in `crm/app/repository.py:1074`; dashboard displays application result as status plus id slice in `app/src/pages/DashboardPage.tsx:100`. | Search gets slower as rich AI content grows, and application results are hard for users to recognize. | Add indexed/full-text search, searchable application company/job fields, and result summary fields like company name, job title/link, status, updated date. |
| UXPERF-008 | High | Agent queues | Agent queue endpoints scan all matching applications/companies and return full objects. | Agent pending routes call `list_applications_by_status()` in `crm/app/main.py:1178`; that method scans all applications at `crm/app/repository.py:876`. | UXPERF-009 | High | Application detail API | Application detail bundles PPA emails with per-PPA scans over all emails. | Detail route loops PPAs and calls `repo.list_emails_for_ppa()` at `crm/app/main.py:719`; `list_emails_for_ppa()` scans all emails in `crm/app/repository.py:1269`. | Detail load cost becomes O(PPAs * all emails). ## Priority Order
1. Fix repository persistence and query architecture first: UXPERF-001 through UXPERF-004. These are core scalability blockers.
2. Fix dashboard/search/agent queue hot paths next: UXPERF-006 through UXPERF-009.
3. Fix high-risk frontend UX flows: UXPERF-023, UXPERF-025, UXPERF-028, UXPERF-029, UXPERF-032, UXPERF-033, UXPERF-040, UXPERF-042, UXPERF-049, UXPERF-050.
4. Move page-local filters and full-catalog frontend fetches to bounded server APIs: UXPERF-010 through UXPERF-015 and UXPERF-018.
5. Polish user trust/accessibility flows: UXPERF-016 through UXPERF-022 and UXPERF-024 through UXPERF-055.
